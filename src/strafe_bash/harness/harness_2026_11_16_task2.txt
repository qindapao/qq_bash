任务：xo.in 增加对象级动态 Mixin（复盘）---------------------------------------
状态：已实现并提交（提交信息：ADDED: Object-level dynamic mixins for xo）

本文不是最初的任务书，而是按「最初怎么想 → 讨论了什么 → 最后怎么做 → 为什么这么
做 → 验证到什么程度」整理出来的复盘稿，供以后回看与复用。

===============================================================================

一、任务目标
-------------------------------------------------------------------------------
给 Boss 增加增益能力（4 个伤害阶段、最多同时持有 2 个、满了随机替换掉一个），
用它来验证 xo.in 新增的「对象级动态注入」——不是初始化阶段的类级注入。

对机制的要求：
  - 创建快、消灭快
  - 能卸掉某个特定能力，也能卸掉全部能力
  - 不能影响帧率（项目唯一硬指标）

===============================================================================

二、最初草案：生成对象级函数（已否决）
-------------------------------------------------------------------------------
草案思路（伪代码）：

    xo_obj_call ()
    {
        if declare -F "${1}_${2}" ; then
            "${1}_${2}" "$1" "${@:3}"
        else
            "${XO_OBJ_POOL[$1]}_${2}" "$1" "${@:3}"
        fi
    }

    xo_obj_mixin_add    # eval 生成 对象名_方法，记录到 XO_METHOD_OBJ_INHERITED
    xo_obj_mixin_delete # 完整扫描方法链，unset -f 注销函数

否决理由（四条，都是硬伤，不是风格问题）：

  1. 同名方法不会回退
     两个 Mixin 提供同名方法时，靠 declare -F 判断「先加的赢」，后加的没生成函数。
     删掉先加的那个之后，后加的永远不会出现 —— 对象静默丢能力。

  2. 删除是 O(对象 × 方法)
     要反查「这个 Mixin 在这个对象上生成了哪些函数」，只能扫全表。

  3. 每次 add 都要 compgen 全表扫描
     compgen -A function 枚举当前 shell 全部函数（本仓库启动后 367 个）。
     Boss 一局只加几次无所谓，但 API 一旦泛化就是 O(函数数)/对象。

  4. 污染全局函数命名空间
     框架有三处按前缀枚举函数（_xo_init_class / xo_class_methods / 类方法注入），
     生成的 OBJ_123_ram 会让「函数名 = 类名_方法名」这个隐含约定出现例外。

三、最终方案：查表分派，不生成任何函数
-------------------------------------------------------------------------------
状态只有对象字段 {OBJMIX} 加三张全局表，增删都是普通数组读写：

    {OBJMIX}            "M_A M_B"            对象持有哪些 Mixin（名单，顺序=优先级）
    XO_MIXIN_METHODS    "M_A" -> "ping solo"  每个 Mixin 提供哪些方法（首次用时算一次）
    XO_OBJ_METHOD       "OBJ_x|ping" -> "M_A_ping"   路由表（唯一的分派依据）
    XO_OBJ_MIXED        "OBJ_x" -> 1          当前哪些对象持有动态能力（bury 门控用）

分派路径：

    xo_obj_call obj method
      ├─ 命中 XO_OBJ_METHOD["obj|method"] → M_<mixin>_<method>
      └─ 未命中 → 回落类的 xo_call（对象没有动态能力时行为与 xo_call 完全一致）

增删路径：

    add    查缓存 → 写路由（先加先赢）→ 名单追加到末尾
    delete 名单摘掉 → 对「被删 Mixin 的每个方法」重新问：剩下的名单里谁最先提供它？
           有人接任就改指向，没人接任就删掉这条路由

关键点：路由表永远由「当前名单」推导，没有任何记忆状态，所以不存在记忆过期。
「接任者后来也被删」不需要特殊处理，走的是同一套重算逻辑。

四、讨论中的三个取舍
-------------------------------------------------------------------------------

4.1 「模板默认能力」被否决
    曾经实现过 xo_obj_mixin_apply_defaults（把模板里的 {OBJMIX} 在 born 后应用）。
    讨论后删除：模板是声明式的，objmixin 是运行时行为，混在一起就要额外解释
    「出厂能力算不算对象能力、能不能单独卸」。类想「出厂自带能力」，在自己的
    _born 钩子里调一行 xo_obj_mixin_add 即可 —— 现成机制，不需要框架新入口。

4.2 模板必须预声明 {OBJMIX}（有实验依据）
    对比实验（同一台机器、同一个 xo.sh）：

      检查项                              声明 '{OBJMIX} => '   不声明
      ----------------------------------  --------------------  ------
      类对象里有该节点                    有                    无
      add 直接赋值（无需 x_insert）       成功                  成功
      xo_get / xo_set                     成功                  成功
      x_walk 能遍历到                     能                    不能

    结论：不声明不是「会触发重型树插入」，而是「字段在对象树里看不见」，
    x_walk / x_dump / 将来任何基于树的序列化都会漏掉它。所以模板声明空字段
    是零成本的正确做法，并在 add 里加守卫，漏声明直接报错而不是造野字段。

4.3 公共 clear 被降级为私有
    最初暴露了 xo_obj_mixin_clear（只清路由、不动名单）。这是个坑：名单说
    「有 M_A」而路由里没有条目，能力就「挂名但调不到」，且 add 会因为名单已有
    M_A 而幂等跳过 —— 永久修不回来。
    改为私有 _xo_obj_mixin_drop_table，只允许在「名单为空时清残留」使用；
    公共卸载入口只有 xo_obj_mixin_delete。

五、最终 API
-------------------------------------------------------------------------------
公共：
    xo_obj_mixin_add obj M_Xxx        注入。幂等；同名先加先赢；Mixin 无方法或
                                      类模板未声明 {OBJMIX} 时报错返回 1
    xo_obj_mixin_delete obj [M_..]    卸载。不传参 = 全部；删后重新解析回退
    xo_obj_mixin_list obj             读名单到 REPLY（空格分隔，无前后空格）
    xo_obj_call obj method [args]     查路由分派，未命中回落类方法

内部：
    _xo_mixin_methods mixin           取该 Mixin 的方法列表到 REPLY（带缓存）
    _xo_obj_mixin_drop_table obj      只删路由；仅限名单为空时用

语义与不变量：
  1. {OBJMIX} 顺序就是优先级，靠前的赢（与类级 {MIX} 语义一致）
  2. 删除后按剩余名单重算，接任者继续被删则继续往后走，最后没人接就删路由
  3. 重新 add 的 Mixin 排到名单末尾 —— 不恢复它原来的优先级
  4. add 幂等：名单里已有就直接返回
  5. 私有方法（M_Xxx__foo）不注入（compgen 的 '[!_]' 规则）
  6. 热路径继续用 xo_call，一行未改；只有需要动态能力的调用点用 xo_obj_call
  7. 对象 bury 时框架负责清路由（两级门控），具名句柄重建不会串味

六、关键实现点与理由
-------------------------------------------------------------------------------

6.1 方法缓存 _xo_mixin_methods
    只扫「这一个 Mixin」的函数（compgen -X '!M_X_[!_]*'），不做全局 M_* 分组：
    Mixin 名带下划线时不会歧义。首次使用算一次，之后永远查表。
    这一步同时替掉了草案里每次 add 的全表扫描。

6.2 add 的顺序很重要
    守卫（类模板必须声明）→ 名单为空时先清残留路由（具名句柄重用）→ 幂等判断
    → 逐方法写路由（已有就跳过 = 先加先赢）→ 名单追加 → 登记 XO_OBJ_MIXED。
    顺序错了会有两类 bug：先登记再清残留会自己擦掉刚写的东西；
    先写路由后查幂等会让重复 add 变成「重新入队」。

6.3 delete 的重解析（未来读者最容易看不懂的一段）
    三层循环分别对应一句话的三个词：
        for d in drop          被删掉的 Mixin
          for m in d 的方法    它提供过的每个方法
            for k in keep      剩下的名单，按原顺序
              第一个能提供 m 的接任；没人接任就删掉这条路由
    keep 保持原顺序，所以「第一个提供者」正好是 add 时该赢的那个 —— 回退用的
    是同一条规则，不会出现「回退到第二个却让第三个赢」。

6.4 bury 的两级门控
    xo_obj_bury 里：
        (( ${#XO_OBJ_MIXED[@]} )) && [[ -n "${XO_OBJ_MIXED[$obj]+_}" ]] && 清路由
    第一级是数组长度判断（O(1)，普通情况下为 0，所有 bury 一步返回）；
    第二级才是 hash 查询，只在「确实有对象带动态能力」时才发生（例如 Boss 战）。
    子弹永远不在集合里，第二级对它们必然落空，不会误清。
    为什么不做成零开销：任何守卫本身都有成本，而框架自己负责清理才能保证
    逻辑自洽（不依赖调用方纪律）。

七、性能
-------------------------------------------------------------------------------
| 场景                                 | 对象销毁时的额外开销                          |
| 没有任何对象带动态能力（平时）        | 1 次 ${#XO_OBJ_MIXED[@]}，不查 hash            |
| Boss 带着能力在场，杀的是子弹         | 多 1 次 hash 查找（落空返回）                 |
| 杀的对象自己带能力                    | 1 次 hash 命中 + 扫它自己的少量路由           |
| 项目完全不用对象 Mixin                | 只有第一档，永远是一次长度判断                |

热路径：xo_call 一行未改，子弹/敌弹/敌人/掉落仍走它。
xo_obj_call 命中时与 xo_call 同为「一次 hash 查询 + 调用」，未命中多一次查询；
只用于每帧个位数次的能力调用点。

测量说明：本机 bash 微基准三次尝试全部不可信（空循环测出 6 µs/次、带门控的版本
反而比裸查询更快，明显被系统调度污染）。所以本文不给微秒数字，只给结构分析与
调用量；帧率结论以真实终端体验为准。

八、测试
-------------------------------------------------------------------------------
单测 test/bashlib/test_xo_obj_mixin.sh，11 个用例：
  1  注入后可调用 + 类方法仍可回落        7  模板未声明 {OBJMIX} 时守卫拒绝
  2  卸载后能力消失、路由不残留           8  全卸载只影响该对象
  3  同名先加先赢 + 删除后回退            9  删不存在的 Mixin 无副作用
  4  幂等                                10  一次删多个、路由全清
  5  无方法的 Mixin 报错                 11  多级回退链（A→B→C→消失）
  6  具名句柄重用不串味

综合场景 test/bashlib/test_xo_obj_mixin_scenario.sh，13 个阶段 / 49 项断言：
  类层级 Base→Entity→Mob→Boss，Mob 手写 act/health/absorb、Boss 覆盖 act，
  类级 {MIX} 给 Mob 注入 M_Shield，对象级用 M_Fire/M_Ice/M_Wind/M_Absorb 混跑。
  覆盖：无能力时等价 xo_call、对象隔离、盖过类方法/继承方法/类级 Mixin、
  同名先加先赢、回退链、重加排末尾、私有方法不注入、契约守卫、bury 重建、
  删不存在、全卸载、方法集首次扫描后固定。

测试过程中发现并处理的问题：
  1. 【真 bug，已修】bury 后同名句柄重建，旧路由残留 → 新对象凭空继承旧能力。
     修法就是 6.4 的两级门控 + XO_OBJ_MIXED 集合。
  2. 【测试自身的 bug】断言辅助函数 r() 没清 REPLY，调用失败时读到上一次的残留值，
     造成 3 个假失败。教训：任何"期望调用失败"的断言都要先清返回值。
  3. 【认知修正，不是 bug】Boss 没写 absorb，但它从 Mob 的类对象继承了 {MIX}，
     于是 Boss 这一层的 Mixin 注入发生在继承透传之前 → Mixin 压过 Mob 的手写实现。
     这符合文件头写明的优先级（类自身 > Mixin > 继承透传），
     类侧代码一行未动，只改了我的断言对象（改用 Mob 实例验证"自身 > Mixin"）。

九、遗留与边界
-------------------------------------------------------------------------------
  - 方法集在「该 Mixin 第一次被使用」时固定（与 xo_init 时类级注入的时机一致）：
    所有 Mixin 方法都必须在第一次 add 之前定义好。测试里有专门用例固化这条。
  - 对象存档不携带路由：读档后需要重新 add。Boss 不存档，当前不受影响。
  - 路由清理由框架负责（bury）+ add 兜底（名单为空时清残留）双保险。
  - 后续待做：Boss 玩法的实际接入（4 阶段 / 最多 2 个增益 / 满了随机替换），
    以及"增益 Mixin 提供哪些方法"的游戏层设计。

十、复盘要点（下次做类似改动时先看这几条）
-------------------------------------------------------------------------------
  1. 先定数据模型再写循环。这次核心结论就一句「不生成函数，查表」，
     方向定错的话整套实现都要重写。
  2. 类侧冻结是对的。综合测试一跑就暴露了「继承来的 {MIX} 优先级」这种既有语义，
     如果当时顺手改类侧，风险不可控；不动它只需要改自己的断言。
  3. 不要用不可信的测量支撑结论。本机微基准三次全部翻车（还烧掉两次 120 秒），
     要么把测量做到可信，要么只讲结构与调用量。
  4. 契约要能被守卫拦住。模板漏声明 {OBJMIX} 会造出「树里看不见」的野字段，
     加守卫（一次报错）比写三行文档有效。
  5. 单测覆盖「函数」，场景覆盖「流程」。这次的真 bug 是场景测试抓到的，
     11 个单测全绿也没发现它 —— 值得的投入。
