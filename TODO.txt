x.in
    * 性能优化
        *. 从 children 数组中找 token 的数字索引不需要先把它转换成数组然后再找，可以考虑使用类似下面
            这种方法，效率非常高
            https://github.com/akinomyoga/ble.sh/blob/master/src/util.sh
            ## @fn ble/string#last-index-of text needle [n]
            ##   @param[in] text
            ##   @param[in] needle
            ##   @param[in] n
            ##     この引数を指定したとき n 番目の一致を検索します。
            ##   @var[out] ret
            function ble/string#last-index-of {
              local haystack=$1 needle=$2 count=${3:-1}
              ble/string#repeat '"$needle"*' "$count"; local pattern=$ret
              builtin eval "local transformed=\${haystack%$pattern}"
              if [[ $transformed == "$haystack" ]]; then
                ret=-1
              else
                ret=${#transformed}
              fi
              ((ret>=0))
            }
            当前由于token是Q字符串，所以如果夹带了索引，要一起寻找匹配Q字符串+ID。
    * 边缘BUG排查
        * 脏键/丢键审计（灾备预案）：
            目前未发现异常，暂不实现。未来出现玄学问题（如内存泄漏、找不到节点）时启用。

            【实现方式】独立封装为 x_verify_tree 函数，严禁修改 x_walk 本身！
            函数内调用 x_walk 做一次从根节点的全量遍历，同时统计访问到的有效 KV 数量。

            【计数规则（极易写错，必须对称）】
            遍历回调中，对每个节点精确累加：
                节点自身的存在感     +1
                节点 .t (类型)      +1 (若有)
                节点 .k (物理路径)   +1 (若有，叶子)
                节点 .s (子节点列表) +1 (若有，容器)
                节点 .c.{key} 映射  +1 (遍历 .s 里的对象键，每个算 1)
            遍历结束后，手动补上未被 x_walk 遍历到的内部键：
                根节点的 .t         +1
                max_index           +1

            【比对逻辑】
            若 统计总数 != ${#tree[@]} ，说明存在“幽灵键”或“孤儿映射”，直接 die 报错。

            【调用时机（信任点主动调用，严禁进热路径）】
            1. 游戏存档 (save_game) 之前 / 读档重建之后。
            2. 测试用例 (test.sh) 的收尾阶段。
            3. x_init 初始化一个复杂的类对象之后。

    * Tcl 9 迁移（远期，待评估）
        * 不用 TclOO：xo 系统整体平移。
          - 对象句柄：`upvar #0 ::xo::obj_$h` 起别名，等价于 bash 的 `local -n`；
          - 方法扫描：`info procs` 替代 `compgen -A function`（无 fork，结果可直接进 list）；
          - 类模板：注册时直接存进 dict（`::xo::templates`），不再靠变量名扫描，
            连 `compgen -A variable` 那一类开销都不存在。
          - 取消 `$X` 与 `{}` 拼接：Tcl 原生嵌套 dict，元键改用保留前缀（如 `__cls`
            `__sup` `__mix`），字段名禁止 `__` 开头；模板继承用 `dict merge`。
          - 扁平/树的区别只保留为语义：扁平 = 没有 `children` 键；有 `children`
            就是树。游戏对象字段仍放顶层，热路径 `dict get $o hp` 不做多一层间接。
        * 先写"同工作量微基准"：200 发弹的 tick、100×30 差分渲染、输入轮询，
          用真实数据判断 Tcl 9 能不能稳定 60 帧，再决定是否迁移。
        * xo vs TclOO 分派微基准（迁移前必跑，三方对比）：
          - 基线：直接 `$cmd $h m` 普通 proc 调用；
          - xo：缓存好的分派表（一次 dict 查 + 直接调用，运行时不许拼命令名、
            不许 `info commands`、不许 eval）；
          - TclOO：`$o m`（含方法查找 + 调用上下文）。
          - 测法：10 万次/组，空方法体，min of 3；再补一组"方法内读写 2~3 个字段"。
          - 验收：xo 分派开销 ≤ 1.5× 直接 proc 调用；若 xo 反而比 TclOO 慢，
            先查分派表设计（是否在运行时拼名字/查命令），改完再谈迁移。
          - 附带测对象开销：dict 对象创建/销毁 vs `oo::object create/destroy`，
            确认"dict 对象更轻"这个假设。
        * 迁移时保留现有架构：SoA 弹幕数组、差分帧缓冲、对象池 + 类模板、
          tick/render 双节拍、消息行/横幅分层。
        * 数据结构取舍：默认 AoS（"list of dict"，真正的结构体数组），
          可读性/可维护性优先；性能不是瓶颈就不引入 SoA。
          只有 200 发微基准证明瓶颈确实在数据结构时，才对敌弹热点做局部 SoA 化，
          不做全盘 SoA。最终以数据为准，不凭感觉。
        * Tcl 9 的加成点：expr 字节码（算术不再走 bash 展开）、无子 shell fork、
          原生 list/dict、UTF-8/64 位整数。
          按当前 26ms/帧估算，Tcl 版 tick+render 有望落在 6–13ms；
          若微基准确认，60 帧（16.7ms 预算）可行。
        * 已知陷阱（移植时逐条对照）：
          - dict 写时复制：proc 参数是值拷贝，改字段前先
            `upvar #0 ::xo::obj_$h self` 再 `dict set self ...`，否则整本字典被复制；
          - 用 `upvar #0` 而不是 `global`，因为 `::xo::obj_*` 是命名空间变量；
          - 列表只在变量之间传递，别经过 format/split：保住内部表示，lset 才是 O(1)；
          - `dict get $o a b` 要求中间层存在；x_get 的"不存在返回空"用 `dict exists`；
          - `dict merge` 是浅合并，模板继承的深合并要按字段递归或逐类展开；
          - 方法列表在类注册时缓存（类 → list），别在调用点反复 `info procs`。
        * 输入/终端（最大的不确定项）：
          - 非阻塞 stdin：`chan configure stdin -blocking 0 -buffering none` +
            `chan pending` 判可读；鼠标 SGR 序列自己解析（规则与 bash 版一致）；
          - 终端 raw 模式、退出恢复要分别在 mintty 和 Linux 终端实测；
          - 定时器：Windows 的 `after` 约 15.6ms 粒度，帧节拍用累加器补拍，
            不能假设 `after 16` 精确；
          - 60 帧的隐形上限可能是终端消费能力，微基准必须包含真实写屏。
        * 字符宽度：Tcl 的 string length 是码点数，不是显示宽度；仍需自带
          wcwidth 表（宪法 §5 的双宽规则原样搬过去）。
        * 测试与迁移路线：
          - 先搬"同工作量微基准"（200 发 tick、100×30 差分渲染、输入排空），
            数据出来再定 30/40/60 帧目标；
          - 现有 shell 测试逐条对照移植（对象系统、弹幕、存档、渲染）；
          - 存档兼容：优先让 Tcl 版直接读旧 bash 存档（JSON 结构一致），
            不行就提供一次性转换脚本。
        * 目标帧率：Linux 稳定 60 帧，Windows 稳定 45 帧（微基准 + 终端实测后定档）。
          底线不变：200 发弹先稳住 30 帧，再往上冲。
        * 语言选型：Go 不考虑——终端游戏是 I/O 密集 + 小计算，Go 性能过剩，
          且字符串/终端模型写起来别扭、代码会更丑；Tcl 的 list/dict 与"画格子"
          天然合拍。
        * 维护策略（2026-11-20 调整）：
          - **Bash 版继续加新功能/新机制**，不做功能冻结；唯一硬约束是**不能影响帧率**：
            只要明显拖慢帧率就违背宪法，必须先优化或放弃该功能。
          - 每个新功能/新机制合入前必须量 tick/render（分段计时），并在 200 发弹压力场景
            下验收；"感觉不慢"不算验收。
          - Tcl 9 仍是远期独立项目，不阻塞 Bash 版的功能推进；两边并行维护。
          - Bash 版继续修 BUG、做小幅平衡，并承担新玩法的主要开发。
        * 项目形态：Tcl 9 是**另一个新项目**（独立 git 仓库），到时候由用户指明路径；
          Bash 版存档暂不迁移，兼容方案到新项目再定。
        * 宪法/文档的 Tcl 版适配：保留通用原则（热路径约束、双宽字符、注释要求、
          字段声明），删掉 bash 专属条款（set -u、eval 引号、compgen 等），
          迁移时一起整理成 Tcl 版 CONSTITUTION.md。
